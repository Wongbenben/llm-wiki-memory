# 6. 反思

## 預測 vs 實際
| | 內容 |
|---|---|
| 我原本預測 | **關卡2 來源檢查最容易出錯**：AI 標了 [S1]，但 S1 其實沒寫這句（張冠李戴） |
| 實際最常出錯 | **關卡2**：6 節的第 1 輪**全部 FAIL**（共 6 次），第 2 輪全部 PASS，沒有用到第 3 輪（見 `wiki/log.md` 的 section-1～6 紀錄、`docs/05-token-log.md` 第 9～21 列）。關卡3 FAIL 1 次、Lint FAIL 1 次。 |
| 預測對了嗎？為什麼？ | **節點猜對，錯誤類型猜錯一半。** 6 次 FAIL 分成兩類：① **沒標來源的總結句／推論**（第 1、2、5、6 節，4 次）：AI 寫教學文時很自然會補一句「換句話說……」「結論就是……」，這種句子在原文裡根本找不到。② **證據格式問題**（第 2、3、4、5 節）：原文有 markdown 粗體、程式碼標記，或摘錄裡有「\|」把表格切壞，這是檢查器的假警報，不是內容錯。真正的「張冠李戴」檢查器**一次都沒抓到**，3 處都是我在 PASS 之後人工複讀才發現的（見下表）。 |

## 我改了哪一步
- **改了 1：關卡2 從「AI 自己貼原文說有對到」改成「程式比對」**（`scripts/check_sources.py`）。每個 [S#] 都要在 `output/evidence-N.md` 有一列英文原文，程式去 `raw/` 確認原文真的存在。這讓「貼原文」變成可以重跑、不會說謊的檢查。
- **改了 2：把檢查往前移到節點2**。寫句子的同時就寫證據表，「找不到原文就不寫」。總結句、推論句在寫的當下就會卡住，不用等到關卡2 才 FAIL。（已寫進 `prompts/02-section-loop.md` 的 v2 修改）
- **改了 3：關卡2 加上人工語意複讀**。程式只能證明「這段原文存在」，不能證明「句子的意思等於原文」。第 5、6 節的 3 處語意錯誤都是這一步抓到的。
- **改了 4：修正檢查器的格式正規化**（第 3 節之後）。拿掉 markdown 的 * 和 `，前 4 節有 3 次是這種假警報。改完重跑第 1～4 節仍然 PASS，沒有放寬內容比對。
- **改了 5：log 時間一律用系統時間**。一開始 agent 預填了還沒到的時間（例如 15:15，實際才 14:51）。log 規定只能往後加，所以只能追加一筆更正，舊紀錄不改。
- 改之前 → 改之後：第 1～4 節每節第 1 輪都 FAIL；第 5、6 節開始「先寫證據」後仍各 FAIL 1 次，但 FAIL 的內容從格式假警報變成真正的內容問題（沒來源的句子、語意多講），也就是說檢查變得更準，而不是更鬆。

## Token 觀察（扣主題）
- **最耗 token 的是 Ingest（約 5 萬，佔全部約 10 萬的一半）**。原因是要把原始資料整份讀進 context；S5 有 155k 字元，大部分是範例程式碼，我只讀說明段落才沒有更多。這正是 S1 說的：讀進來的東西全部算進 context window，而且之後每一輪都會跟著重送。
- **「只讀 index、只開需要的頁」這次沒有省到**。因為 ingest、大綱、逐節寫都在同一個 session，概念頁早就在 context 裡了，大綱「只讀 index」只是形式上的。要真的省，應該在每個節點之間 `/clear` 或開新 session，這時 index 才會變成真正的「目錄先載、內容要用再拿」（就像 S3 說的自動記憶只載入 MEMORY.md 索引）。
- 表上的 token 是估算值，而且**低估了**：每一次工具呼叫都會把之前整段對話再送一次（S1 的每輪累積），實際送出的輸入 token 會比表上多很多，只是重複的前綴有 prompt caching 打折（S5）。

## 下次會怎麼改
1. **每個節點開新 session 或先 `/clear`**，讓「只讀 index」真的省到 token，也讓各節的 token 數可以分開量。
2. **證據表要多一欄「這句有沒有比原文多講」**，讓人工語意複讀變成檢查清單上的一格，不是靠記得去做。也考慮在 AGENTS.md 加一條規則：「總結句、推論句也要有原文，不然就不寫」。
